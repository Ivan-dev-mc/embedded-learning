## ЧАСТЬ 1. БАЗА: ИНСТРУМЕНТЫ, C, ЖЕЛЕЗО (0–3 мес.)

### 1.1 Рабочее место без боли
🧠 Среда должна компилировать и шить, а не отвлекать.  
🔧 VS Code, PlatformIO, `framework = espidf`, Git, структура проекта.  
🧪 Создать проект, настроить порт, залить пустой шаблон, зажечь встроенный LED через `gpio_set_level()`.  
💥 Ошибка драйвера/прав доступа → порт не виден. Чиним: проверка `lsusb`/диспетчера, reinstall CP210x/CH340, добавление в `dialout`.  
✅ Проект собирается, шьётся, LED мигает, первый коммит в Git.

### 1.2 C для железа: память и регистры
🧠 МК не прощает утечек, висячих указателей и оптимизированных чтений.  
 Указатели, битовые маски, `volatile`, `const`, карта памяти (Flash/RAM/Peripherals).  
 Прямая запись в регистры GPIO (без HAL/Arduino-обёрток), чтение состояния пина через регистр.  
💥 Забыл `volatile` → компилятор закэшировал значение → данные устарели. Чиним: добавляем `volatile` к регистрам/флагам.  
✅ Понимаешь, где лежит код/данные, умеешь работать с битами, регистры читаются корректно.

### 1.3 Электроника и макетка
🧠 Код управляет током и напряжением. Ошибка в расчёте = дым.  
🔧 Закон Ома, логические уровни (3.3V), pull-up/down, ток пина, мультиметр.  
🧪 Схема LED + кнопка на макетке. Рассчитать и поставить резистор, измерить ток, проверить подтяжку.  
💥 Подключил LED без резистора → спалил пин/LED. Чиним: R = (3.3V - Vf) / If.  
✅ Схема собрана, ток в норме, кнопка меняет состояние пина, мультиметр в руках.

### 1.4 Прерывания и таймеры (Bare-metal)
 `delay()` блокирует всё. Прерывания и таймеры работают в фоне.  
 GPIO Interrupts, Timer/Counter, SysTick, программный антидребезг.  
🧪 Мигание по таймеру (не delay), кнопка меняет частоту через прерывание + флаг в главном цикле.  
💥 Прерывание срабатывает 10 раз на 1 нажатие (дребезг). Чиним: таймаут 50мс или сброс флага после обработки.  
✅ LED мигает точно, кнопка реагирует мгновенно, цикл `while(1)` не блокируется.

ESP32, кнопка → LED. Частота мигания управляется кнопкой. Только регистры/IDF low-level, прерывания, антидребезг. Коммит, схема, README.

## ЧАСТЬ 2. ПЕРИФЕРИЯ, RTOS, C++ (3–6 мес.)

### 2.1 Протоколы связи: UART, I2C, SPI
🧠 Чипы общаются байтами по проводам. Шина может зависнуть.  
🔧 Кадры данных, baud rate, master/slave, таймауты, обработка `NACK`/ошибок.  
🧪 Подключить BME280 по I2C, считать данные, обработать таймаут шины без зависания задачи.  
💥 Забыл подтяжку на SDA/SCL или перепутал пины → шина висит. Чиним: проверка wiring, логический анализатор/осциллограф.  
✅ Датчик отдаёт данные стабильно, код обрабатывает сбой шины, задача не блокируется.

### 2.2 FreeRTOS: многозадачность
🧠 Одно ядро, много дел. RTOS переключает контекст.  
🔧 Задачи (`xTaskCreate`), планировщик, очереди (`xQueue`), семафоры, приоритеты, инверсия приоритетов.  
🧪 Задача 1: опрос датчика (1 сек). Задача 2: вывод в Serial. Обмен данными через очередь.  
💥 Очередь переполнилась → `xQueueSend` заблокировал задачу навсегда. Чиним: таймаут отправки + обработка `pdFALSE`.  
✅ Задачи работают параллельно, данные не теряются, система стабильна под нагрузкой.

### 2.3 Управление питанием
🧠 Батарея не бесконечна. МК должен спать, а не молотить вхолостую.  
 Light/Deep Sleep ESP32, пробуждение (Timer/EXT0), RTC память, профилирование тока.  
🧪 Цикл: Проснулся → Считал датчик → Отправил в Serial → Ушёл в Deep Sleep на 60 сек.  
💥 Забыл сконфигурировать пробуждение или не закрыл периферию → ток в сне > 1mA. Чиним: `esp_sleep_enable_timer_wakeup()`, `gpio_hold_en()`.  
✅ Ток в сне < 10–20µA, просыпается сам, данные в RTC сохраняются.

### 2.4 C++ для Embedded
🧠 Абстракции нужны, но куча и исключения убьют МК.  
 Классы-драйверы, RAII для инициализации, `std::array` (статика), запрет `new`/`delete`/`exceptions`, `noexcept`.  
🧪 Переписать драйвер BME280 на C++ класс. Сравнить размер бинарника и RAM с C-версией.  
💥 Случайно вызвал `new` или бросил `throw` → линкер добавил кучу/обработчики → крах/рост прошивки. Чиним: `-fno-exceptions -fno-rtti`, статические пулы.  
✅ Код структурирован, размер не вырос, нет динамической памяти, компилятор ругается на запрещённое.

ESP32 + BME280 + OLED. FreeRTOS (2 задачи), Deep Sleep между циклами, данные в LittleFS, C++ драйверы. Коммит, замеры тока, README.

## ЧАСТЬ 3. СВЯЗЬ И IOT-ПРОТОКОЛЫ (6–9 мес.)

### 3.1 Wi-Fi и TCP/IP на ESP32
🧠 Беспроводная сеть — ненадёжный канал. Код должен переживать обрывы.  
🔧 STA/AP режимы, lwIP стек, DNS, HTTP клиент, обработка `WIFI_EVENT_DISCONNECTED`.  
🧪 ESP32 подключается к Wi-Fi, раз в 10 сек шлёт GET-запрос, парсит JSON, при обрыве — переподключение с таймаутом.  
💥 Код висит в `while(WiFi.status() != WL_CONNECTED)`. Чиним: конечный таймаут + возврат в FSM/задачу + повторная попытка.  
✅ Соединение восстанавливается автоматически, запросы идут по расписанию, задача не виснет.

### 3.2 MQTT и TLS
🧠 Легковесный протокол для IoT. Шифрование обязательно в продакшене.  
🔧 Брокер, топики, QoS 0/1/2, Last Will, TLS-сертификаты, `esp-mqtt`.  
🧪 Поднять Mosquitto. ESP32 публикует данные по MQTT over TLS. Python-скрипт подписывается, пишет в SQLite.  
💥 Сертификат просрочен/не тот CA → TLS handshake fail. Чиним: обновление CA-bundle, проверка даты, `insecure` только для отладки.  
✅ Данные летят по шифрованному каналу, брокер принимает, бэкенд сохраняет, Last Will срабатывает при обрыве.

### 3.3 Промышленные протоколы (Обзор)
 В цехах и щитах говорят на Modbus/CAN, а не на MQTT.  
🔧 Modbus RTU/TCP (регистры, функции, Endianness), CAN (фреймы, арбитраж) — концептуально.  
🧪 ESP32 как Modbus Slave: отвечает на запросы "Read Holding Registers" от ПК (QModMaster).  
💥 Неправильная раскладка регистров → клиент читает мусор. Чиним: проверка Big/Little Endian, адресации, типа данных.  
✅ ПК читает данные с ESP32 по Modbus, значения корректны, код не блокирует шину.

## ЧАСТЬ 4. АРХИТЕКТУРА НАДЁЖНОГО ПО (9–12 мес.)

### 4.1 Конечные автоматы (FSM)
🧠 Сложная логика без спагетти-кода и флагов-костылей.  
🔧 Состояния, события, переходы, таблица FSM, enum/struct реализация.  
🧪 FSM управления устройством: IDLE → WORK → FAULT → RECOVERY. Логирование каждого перехода.  
 Забыл обработать событие в текущем состоянии → система игнорирует воздействия. Чиним: полная матрица переходов + `default`-обработка.  
✅ Логика предсказуема, код читается, текущее состояние всегда известно и логируется.

### 4.2 Отказоустойчивость
🧠 Всё ломается: сеть, датчик, питание. Система должна деградировать безопасно.  
 Watchdog (Hardware/Task), Retry с exponential backoff, Circuit Breaker, Graceful Degradation.  
🧪 Симуляция обрыва сети/датчика. Система пишет в лог, переходит в fallback-режим, восстанавливается сама.  
💥 Watchdog не сбрасывается в длинном цикле → постоянный ребут. Чиним: `vTaskDelay()` или ручной `esp_task_wdt_reset()`.  
✅ При сбое система не виснет, логирует, восстанавливается, данные не теряются.

### 4.3 Хранение и буферизация
 Сеть пропала → данные не должны исчезнуть. Flash имеет лимит циклов записи.  
 Кольцевой буфер (Ring Buffer), LittleFS, wear leveling, чанковая отправка.  
🧪 При обрыве MQTT данные копятся в Flash (до 1000 записей). При восстановлении — отправляются пачками.  
💥 Flash износился/переполнился → запись падает. Чиним: проверка статуса LittleFS, удаление старых записей (FIFO), `esp_littlefs` wear-leveling.  
✅ Данные переживают обрывы, Flash не переполняется, отправка стабильна, износ равномерный.

### 4.4 Безопасность и OTA
🧠 Обновление "по воздуху" без превращения устройства в кирпич.  
🔧 Secure Boot, Flash Encryption, OTA partitions (A/B), подпись прошивки, atomic update.  
🧪 Настроить OTA через HTTPS. Залить новую версию, проверить откат при ошибке валидации.  
💥 Прошивка битая → устройство в бутлупе. Чиним: проверка хэша/подписи перед `esp_ota_begin`, fallback на рабочую партицию.  
✅ Обновление проходит гладко, при сбое — откат, устройство живо, загрузка защищена.

## ЧАСТЬ 5. ПРОФЕССИОНАЛЬНАЯ РАЗРАБОТКА (12–18 мес.)

### 5.1 Тестирование логики и CI
🧠 Код без тестов — лотерея. Рефакторинг без страховки — риск.  
 Unity/CppUTest, моки железа, статический анализ (`cppcheck`), GitHub Actions (базово).  
 Вынести логику FSM в отдельный `.c/.cpp` файл без зависимостей от IDF. Написать 5 тестов на ПК. Запускать в CI при пуше.  
💥 Тесты проходят на ПК, но падают на железе из-за таймингов. Чиним: разделение логики и драйверов, мокирование времени/шины.  
✅ Логика протестирована изолированно, CI зелёный, рефакторинг безопасен.

### 5.2 Глубокая отладка (Когда Serial не хватает)
 Иногда нужно заглянуть внутрь ядра после краша.  
🔧 Core Dump анализ, `esp_backtrace_parse`, ESP-Prog (JTAG) — только для сложных падений.  
 Намеренно вызвать `panic`, разобрать стек по адресу, найти строку-виновника в коде.  
💥 JTAG не коннектится из-за конфликта пинов или режима отладки. Чиним: отключение других отладчиков, проверка fuse-битов.  
✅ Умеешь читать crash-логи, находишь причину падения без гадания, используешь JTAG только когда нужно.

### 5.3 Архитектура и HAL
🧠 Код должен жить дольше одной платы и одного датчика.  
🔧 Hardware Abstraction Layer, разделение на слои (Drivers / Middleware / App), интерфейсы вместо прямых включений.  
🧪 Написать интерфейс `ISensor`, реализовать `BME280Sensor`, подменить на `MockSensor` для тестов. Приложение не знает о железе.  
💥 Приложение всё ещё тянет `#include "bme280.h"`. Чиним: вынос зависимостей в конструктор/инициализатор, передача интерфейса.  
✅ Смена датчика/платы требует правки только в слое драйверов, приложение не трогается, тесты работают на моках.
