## 🧭 Ключевой принцип: Поломка = Задача

**Инсайт:**
> «Поломка — это не катастрофа. Это задача с входными данными (что сломалось), процессом (диагностика → решение) и выходом (работает). Нет паники. Есть алгоритм».

**Как применять:**
1.  **Остановись.** Не реагируй эмоционально.
2.  **Диагностируй.** Что именно не работает? Что изменилось?
3.  **Разбей.** Большая задача → маленькие шаги.
4.  **Решай.** По одному шагу.
5.  **Зафиксируй.** Что помогло — в базу знаний.

**Связь с проектами:**
- [[VPN_personal]] → резервный инбаунд = задача «что если основной отвалится?»
- [[Runout_Scanner]] → чек-лист ошибок = задача «что может пойти не так?»
- [[Pi400_workstation]] → профили на SD = задача «что если система сломается?»

## 🧭 Мета-навык: Алгоритм решения любой проблемы

**Инсайт:**
> «Техника, сети, код — это тренажёры. Настоящий навык — алгоритм: диагностика → декомпозиция → тест → фиксация. Он работает на железе, в отношениях, финансах, здоровье. Поломка ≠ катастрофа. Поломка = задача с входными данными».

**Как применять:**
1. Останови реакцию → собери факты
2. Найди границу проблемы (что ломается, где?)
3. Разбей на 1-3 проверяемых шага
4. Сделай шаг → замерь результат
5. Зафиксируй: что сработало, что нет

**Связь с проектами:**
- [[VPN_personal]] → резерв = шаг «что если отвалится?»
- [[Runout_Scanner]] → чек-лист ошибок = фиксация гипотез
- [[Pi400_workstation]] → профили SD = изоляция сбоев

## ⚡ Инсайт: Цена ошибки (КЗ)

**Ситуация:** Сжег Arduino Nano, перебрасывая провода под напряжением.
**Причина:** Случайное замыкание контактов при коммутации.
**Урок:** Никогда не менять соединения под нагрузкой.
**Правило:**
1. Выключить питание.
2. Проверить цепь мультиметром (прозвонка на КЗ).
3. Включить питание.

> «Лучше потратить 10 секунд на выключение тумблера, чем 300 рублей на новую плату и час на распайку.»

## 🧭 Мой процесс решения задач

**Суть:**
> «Я не копирую первое решение. Я исследую → проектирую → ревью → реализую → анализирую. Это не "долго". Это "надёжно"».

**Этапы:**
1. **Исследование** — изучаю варианты, протоколы, подводные камни

3. **Ревью** — обсуждаю с доверенным лицом (Сильвина), получаю фидбек

**Примеры:**
- [[VPN_personal]] → неделя исследования протоколов → запуск за день
- [[Pocket_engineer]] → сейчас на этапе исследования/проектирования

**Зачем:**
- Меньше отладки «вслепую»
- Больше понимания архитектуры
- Уверенность: «Я не скопировал. Я спроектировал»

## 🧭 Инсайт: Как использовать ИИ как инженер

**Суть:**
> «Нейросеть — не "сделай за меня". Это "сделай мне А, Б, В, чтобы работало Х, У, Z. Объясни почему так. Что если иначе? Не понял — объясни по-другому. Дошло — идём дальше"».

**Почему это важно:**
- ИИ — усилитель, а не замена мышления
- Ты задаёшь направление, ИИ ускоряет исполнение
- Понимание > копирование. Всегда.

**Как применять:**
1. Формулируй задачу конкретно: что, как, зачем
2. Требуй объяснений: «почему так?», «что если иначе?»
3. Не принимай «не понял» как тупик — проси переформулировать
4. Фиксируй: «дошло» → двигайся дальше

**Связь с философией:**
🧭 Моя инженерная философия → контроль процесса, а не зависимость от инструмента

## 🧭 Инсайт: Копипаст — инструмент, а не приговор

**Суть:**
> «Копировать код — не плохо. Плохо — копировать без намерения. Если цель "просто чтобы работало" — копирую, запускаю, решаю задачу. Если цель "научиться" — пишу сам, разбираю, понимаю. Разница — в осознанности».

**Фильтр перед копипастом:**
1. Зачем? (решить сейчас / не думать)
2. Вернусь ли? (разобраться позже / забыть)
3. Понимаю ли риски? (да, с откатом / нет, надеюсь)

**Примеры:**
- ✅ `VPN_Personal`: скопировал конфиг VLESS → но потом разобрал, как работает Reality
- ✅ `Crypto_Monitor`: взял шаблон парсера → но переписал фильтрацию под себя
- ❌ (из прошлого): скопировал код для Arduino → не разобрался → сжёг плату

**Вывод:**
Копипаст — это ускоритель. Но ускоритель без руля — это авария.

##  Шаблон запроса к ИИ: от хаоса к структуре

**Суть:** ИИ достраивает паттерн по входным данным. Мусор на входе → мусор на выходе. Чёткий промпт = техническое задание в миниатюре.

### 📝 Базовая структура
[Контекст] Что делаю / стек / ограничения (среда, архитектура, лимиты)
[Задача] Что нужно получить (конкретно: функция, конфиг, схема, чек-лист)
[Требования] Чего НЕ должно быть (запреты, ограничения памяти/блокировок)
[Входные данные] Код / лог / ошибка / схема (если есть)
[Критерий успеха] Как пойму, что ответ рабочий (компиляция, конкретный вывод, тест)

### ✅ Валидация перед отправкой (Фильтр)
1. **Контекст ясен?** Указан стек и границы (например, `ESP-IDF, FreeRTOS, без динамической памяти`).
2. **Задача конкретна?** Заменено «сделай» на «верни функцию/конфиг X, который обрабатывает Y при условии Z».
3. **Критерий измерим?** Результат можно проверить объективно: сборка без ошибок, конкретная строка в логе, прохождение юнит-теста.

### 💡 Пример заполнения
> `[Контекст]` ESP32, ESP-IDF, FreeRTOS, опрос датчика раз в 5 сек.  
> `[Задача]` Реализовать очередь для передачи данных в задачу отправки.  
> `[Требования]` Без блокировок, таймаут `xQueueSend` = 100мс, обязательная обработка `pdFALSE`.  
> `[Входные данные]` Фрагмент задачи-сборщика: [код].  
> `[Критерий]` Код компилируется, задача не виснет, данные не теряются при переполнении очереди.

## 🧭 Инсайт: Гранулярность промпта = фаза задачи

**Суть:**
> «Расплывчатые указания полезны только на этапе генерации идей или исследования. Когда цель — сделать, разобрать, научиться, интегрировать или повторить — нужна чёткая формулировка. ИИ не читает мысли. Он масштабирует твою структуру».

**Матрица применения:**

| Фаза | Промпт | Результат |
|------|--------|-----------|
| Идеи / Штурм | Открытый, без рамок | Варианты, гипотезы, неочевидные связи |
| Выбор / Сравнение | Полу-структурированный | Плюсы/минусы, критерии, рекомендации |
| Разбор / Обучение | Чёткий + контекст | Объяснение механизма, примеры, границы |
| Код / Конфиг / Отладка | Жёсткий по шаблону | Готовый артефакт, критерий успеха, 0 воды |

**Фильтр перед отправкой:**
- Если цель «придумать» → разрешаю размытость
- Если цель «сделать/разобрать/внедрить» → применяю шаблон [Контекст → Задача → Требования → Критерий]
